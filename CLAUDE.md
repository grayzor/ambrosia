# Ambrosia — guide pour les agents IA

Ambrosia est une « encoche » (notch) pour Windows : un îlot noir toujours au premier plan, en haut au centre de l'écran principal, qui se déplie au survol. Gany (Ganymède, l'échanson qui sert l'ambroisie aux dieux) y vit et prévient l'utilisateur de ce qui compte : sessions Claude Code, mails importants, etc. Inspiré de [coucou](https://github.com/Louis-CFM/coucou) (logique des hooks, machine à états de l'îlot), réécrit en Electron, Windows uniquement.

## Où sont les choses
- `src/main/` — process principal (Node) : `main.js` (fenêtre îlot, tray, IPC, survol), `modules.js` (hôte des modules), `claude.js` (seul accès à l'IA : la CLI `claude -p`), `hook-server.js` (named pipe), `hooks-install.js` (fusion de `~/.claude/settings.json`), `store.js` (réglages JSON), `paths.js`, `log.js`, `system.js` (verrouillage, plein écran, « Ne pas déranger », écrans), `claude-desktop.js` (liens `claude://`), `session-window.js` (retrouver la fenêtre d'une session), `winrt.js` (WinRT via Windows PowerShell 5.1), `speech.js` / `speech-logic.js` (écoute et voix de Gany), `piper-install.js` (voix Piper).
- `src/renderer/` — l'îlot : `island.js` (états encoche / aperçu / ouvert, alertes, humeur), `gany.js` (le personnage, Canvas 2D, aucune image), `sound.js` (lyre synthétisée, aucun fichier audio), `ui.js` (helpers DOM `h()`, `markdown()`), `voice.js` (lecture de la voix de Gany, bouche synchronisée), `style.css` (tokens + classes partagées par les vues).
- `src/settings/` — fenêtre Réglages, générée depuis les schémas `settings` des modules.
- `src/modules/<id>/` — **une feature = un dossier**. `main.js` (Node) + `view.js` (îlot, module ES). Découverts automatiquement.
- `hook/ambrosia-hook.js` — le relais que Claude Code exécute à chaque hook ; `hook/relay-lib.js` ses calculs bon marché (diff de lignes, sortie de tests, consignes) ; `hook/ambrosia-statusline.js` la statusLine relais (jauges du forfait) ; `hook/ambrosia-notify.js` la commande des scripts de l'utilisateur.
- `scripts/` — `deploy.js`, `gen-icons.js`, `new-module.js`, `dev-server.js` (prévisualiser `dev/*.html` dans un navigateur), `build.js` / `smoke-update.js` / `install.ps1` (versions publiées, voir « Mises à jour automatiques »).

## Ajouter une feature (le chemin rapide)
1. `npm run new-module -- <id> "Nom" <icône>` crée `src/modules/<id>/main.js` et `view.js`.
2. Dans `main.js`, `init(ctx)` reçoit :
   - `ctx.setState(patch)` → pousse l'état vers la vue (sérialisable JSON). Mettre `mood: { name, priority }` pour que Gany change d'humeur (`idle, working, thinking, approval, question, waiting, finished, error, mail, sleeping, annoyed, dizzy, love, ratelimit, greet`). Priorités : approbation 100, mail urgent 75, mail 60, travail 40.
   - `ctx.alert({ key, title, text, from, mood, sound, priority, ttl, pin })` → aperçu dans l'encoche. `ctx.dismissAlert(key)`.
   - `ctx.focus(pin)` / `ctx.unpin()` → ouvre l'îlot sur ce module (épinglé tant qu'une réponse est attendue).
   - `ctx.onAction(name, fn)` → appelé par la vue via `ui.action(name, payload)`.
   - `ctx.settings()`, `ctx.setSettings(patch)`, `ctx.onSettings(fn)` ; `ctx.data.load(fallback)` / `ctx.data.save(v)` pour l'état persistant non-réglage.
   - `ctx.claude.run({ prompt, model, systemPrompt, tools, allowedTools, jsonSchema, requireMcp })` → `{ ok, text, structured, error, authError, mcpNotReady }`. Avec `requireMcp: "claude.ai Gmail"`, la question part seulement après une chauffe (12 s, puis 25 s) : le mode headless n'attend pas les connecteurs claude.ai. `ctx.claude.stream(...)` pour du streaming. `ctx.claude.mcpPrefix(serverName)` pour nommer les outils d'un connecteur.
   - `ctx.hooks.on('hook', ev)` → tous les événements Claude Code (`ev.payload`, `ev.reply(answer)` pour les événements bloquants).
   - `ctx.paused()` (pause de l'utilisateur, session verrouillée ou reprise pas encore arrivée : ne lancer aucun nouveau travail de fond), `ctx.pausedByUser()`, `ctx.onResume(fn)` ; `ctx.openExternal(url)`, `ctx.openPath(p)`, `ctx.log(...)`.
   - `ctx.peers()` (états de tous les modules, lecture seule), `ctx.react(mood, ms, { sound, confetti })` (une réaction de Gany sans alerte), `ctx.activity()` → `{ idleMs }` depuis le dernier mouvement de souris.
   - `ctx.setInCall({ title, endsAt } | null)` / `ctx.inCall()` → mode « en appel » (voir plus bas). Déclarer `recap: { one: 'mail', many: 'mails' }` dans le module pour le libellé du récap ; une alerte qui en résume plusieurs porte `count`.
   - `ctx.launchClaude({ cwd, model, prompt, worktree, permissionMode, title, resume, fork })` → `{ ok, sessionId, via, error }` : ouvre Windows Terminal sur une session `claude` **interactive** de l'utilisateur (voir plus bas). Seulement après un clic.
3. Dans `view.js` : `summary(state)` → `{ dots:[{color,pulse}], badge:{text,color}, count, text }` (encoche, onglet, sous-titre) et `render(root, state, ui)` (ou `mount`/`update` si la vue contient un champ texte qui doit survivre aux mises à jour). Utiliser `ui.h` et les classes de `style.css` (`card`, `row`, `btn`, `pill`, `list`, `empty`…).
   Une section peu visitée met `secondary: true` dans sa définition : son onglet va derrière « ⋮ » (liste verticale sous les onglets, le bouton porte leur compteur), et ne revient dans la rangée que quand elle est ouverte (ex. Bilan, Routines, Scripts).
4. Déclarer les réglages dans `settings: [...]` (types : `boolean, number, text, textarea, list, select, button`) : la page Réglages se génère seule.
5. `npm run dev` recharge l'îlot à chaque modification de vue et relance l'app quand un fichier Node change.

## Surveiller une nouvelle source (le chemin encore plus rapide)
Pour « surveille X et préviens-moi de ce qui est important » via un connecteur claude.ai (Gmail, ClickUp, Slack, Calendar…), ne pas écrire de module à la main : utiliser le moteur `src/main/triage.js`, comme `src/modules/mail/` et `src/modules/clickup/`.
- `main.js` : `module.exports = triage({ id, name, icon, color, order, source, connectorPattern, readTools, systemPrompt, defaultRules, steps({ since, firstRun, settings, data }), normalize?, extraSettings?, extraSchema?, onStructured?, labels: { digest } })`. `readTools` = uniquement des outils **en lecture** du connecteur ; `steps` = les appels d'outils à faire pour la fenêtre `since` (ms).
- `view.js` : `export default triageView({ source, where, badge, one, many, feminine?, qualifier?, open, color })` depuis `src/renderer/triage-view.js`.
- Le moteur gère : détection du connecteur, attente qu'il soit prêt, vérification périodique aux heures de veille, déduplication, VIP / ignorés, « Traité », « Pas important » (réinjecté dans le prompt), alertes, humeur de Gany, compteurs, réglages. Tests : `tests/triage.test.js`.
- Avant d'écrire `steps`, sonder les vrais outils du connecteur (dans une session Claude Code) : leurs noms, leurs champs de date, et ce qui est trop volumineux.
- `groupBy(raw)` (optionnel) : une carte par clé (ex. l'url de la tâche ClickUp), la plus grave.
- `itemFields` (optionnel) : champs en plus par élément (ex. le fil Chat), lus par `normalize` / `groupBy`. Si un outil renvoie une erreur, le tour la recopie dans `source_error` : l'onglet l'affiche (`explainError(msg)` pour la traduire) au lieu de « rien d'important ».
- `variant(settings, data)` (optionnel) : lire une autre source pour un temps (`source, connectorPattern, readTools, steps, systemPrompt, label`) ; `onSourceError(err, data, settings)` → `true` relance la vérification aussitôt (après avoir basculé).
- `src/modules/gchat/` (Google Chat) : connecteur « claude.ai Chat MCP », `search_messages` (@mentions, messages directs, ses propres messages pour savoir s'il a répondu), une carte par conversation directe ou par fil. Les rafales de messages courts font **un** élément par sujet (consigne `MERGE`, champ `count`, cartes ouvertes rappelées au modèle par `openCards`) ; filet local : dans un espace, les messages qui ouvrent chacun leur fil sont regroupés par personne (`threadRoot`). Côté moteur, `collapse` additionne les `count`, une carte remplacée passe ses messages à la suivante (`item.messages`, « · 3 messages » sur la carte) et une suite arrivée moins de 30 min après ne refait pas de son. Le serveur MCP de Chat est en préversion : le compte de **chaque** utilisateur doit être inscrit au Google Workspace Developer Preview Program, l'inscription d'un administrateur ne vaut que pour lui (sinon : « Chat MCP access is not enabled for this project ») ; en mode Auto, Gany lit alors les mails de rappel de Chat (`chat-noreply@google.com`, via Gmail, avec retard), que Courrier lui laisse, et réessaie le connecteur toutes les heures.
- `src/modules/drive/` (commentaires Docs/Sheets/Slides) : le connecteur Drive n'a pas de flux de commentaires, donc le module lit en lecture, via Gmail, les mails de notification de Google (`drive/senders.js` : mentions, tâches assignées, réponses, demandes d'accès, partages), une carte par fil de commentaires (`?disco=`). Tant que Drive est actif, Courrier exclut ces expéditeurs de sa recherche.
- `proposer` (optionnel, `propose.js` du module) : pour un élément important tout neuf, un second tour **en lecture seule** prépare ce que l'utilisateur ferait (`make` → `{ headline, ask, analysis, plan, read, text, actions, data }` ou `null` : alors rien ne change, sans un mot). L'alerte attend la proposition (90 s max, `budgetMs`) pour arriver avec elle. Chaque bouton (`apply`) exécute **un seul** outil d'écriture via `callTool(ctx, server, tool, args)` (exactement ces arguments, vérifié dans `toolsUsed`). « Pas utile » (`dismissProposal`) est réinjecté dans les prompts suivants. Réglages ajoutés : `propose`, `proposeModel`, plus ceux du proposer.
  - Courrier (`src/modules/mail/propose.js`) : réponse (Envoyer / En brouillon), ajout à une réunion existante ou nouvelle réunion (via le connecteur de l'Agenda, `peers().agenda.connector`). Jamais de fait, chiffre ou engagement inventé.
  - ClickUp (`src/modules/clickup/propose.js`) : commentaire, statut, réaffectation, « Traiter dans <projet> ». L'analyse lit les projets de référence (réglage `projects` : CLAUDE.md, mémoire `~/.claude/projects/<chemin>/memory`, code) avec Read/Grep/Glob, secrets refusés (`denyRule`). Jamais de Bash en fond : le traitement ouvre une vraie session Claude Code dans le projet, **en mode plan** (`claude.openSession`).

## Lancer une session Claude Code (« Confier à Claude »)
- Chaque carte d'un module `triageView` a « Confier à Claude » ; l'onglet Claude a « + Nouvelle session ». Le formulaire partagé est `src/renderer/launch-form.js` (`launchButton`, `launchOpen`, `launchForm`, `openLaunch` ; ses valeurs survivent aux re-rendus). Il parle au module sans onglet `src/modules/launch/` (actions `options`, `probe`, `launch` ; réglages « Sessions Claude » : dépôts connus, modèle **opus** par défaut, worktree, mode de permission). Logique pure : `src/modules/launch/logic.js` (choix des dépôts, valeurs par défaut, prompt encadré).
- `src/main/launcher.js` : `wt.exe new-tab … powershell.exe -NoExit -EncodedCommand <base64>` (repli : `cmd /c start`). Le script ne contient que des chemins ; les arguments de `claude` (prompt compris) sont échappés selon les règles MSVC (`quoteArg`), écrits dans un fichier temporaire (`%LOCALAPPDATA%\Ambrosia\launch`) et passés tels quels à `ProcessStartInfo.Arguments` : aucun shell ne lit jamais le prompt. Options CLI : `--model`, `--permission-mode` (liste blanche, jamais `bypassPermissions`), `--worktree <nom>`, `--session-id <uuid>`, `--name`, `--resume <uuid>` (`--fork-session` seulement avec), puis `-- <prompt>`. Ou bien Claude Desktop (`launcher.launchDesktop`, voir le module Claude) : choix « Lancer dans » du formulaire ; une reprise part toujours au terminal.
- `--session-id` relie la session au hook `SessionStart` : Gany la salue. La carte d'origine reçoit `delegatedAt` (action `delegated` du moteur de tri), sans être marquée traitée.
- Le contexte externe est encadré par `"""` et présenté comme une donnée ; l'utilisateur relit et modifie le prompt avant « Lancer ».

## Quand il faut du temps réel plutôt qu'un tri
`src/modules/agenda/` montre l'autre modèle : Claude ne sert qu'à **lire** la source en JSON (toutes les 15 min), puis tout est local et déterministe (un ticker toutes les 15 s). `src/main/presence.js` dit si l'utilisateur est en appel (micro tenu par le navigateur dans le registre Windows, fenêtres « Meet - … ») ; ne l'interroger qu'autour des réunions.
Alertes prioritaires : `ctx.alert({ pin: true, actions: [{ label, action, payload, primary, dismiss }] })` → boutons dans l'aperçu ; une alerte épinglée reste jusqu'à la réponse (`dismiss: false` : le bouton ne la ferme pas). Humeurs `meeting-soon/now/late` (sablier, lueur rouge pour now/late).
Brief avant réunion (`agenda/brief.js`, logique pure + tests `tests/agenda-brief.test.js`) : `briefLeadMinutes` avant le début (ou bouton « Préparer »), un `ctx.claude.run` avec les seuls outils en lecture des connecteurs détectés (Calendar `get_event`, Gmail `search_threads`/`get_thread`, ClickUp `clickup_search`/`clickup_get_task`, Drive `search_files`/`get_file_metadata`/`read_file_content`), sortie `BRIEF_SCHEMA` passée par `sanitize()` (liens https seulement). Cache `data.briefs[id]` invalidé par `fingerprint(e)` (heure, titre, invités, `updated`). L'alerte « réunion bientôt » gagne « Voir le brief » ; un lien ne s'ouvre que s'il figure dans le brief.
Agenda, suite :
- **« Me voir »** (`mirror.js`, côté îlot) : miroir de la webcam avant un Meet (bouton de la carte, ou de l'alerte « bientôt »). La caméra ne s'allume que sur un clic, vidéo seule, image inversée (`scaleX(-1)`), rien n'est enregistré ; tout s'arrête à la fermeture, au repli de l'îlot, au changement d'onglet, sur « Rejoindre », quand la réunion est rejointe, validée par OK ou terminée, et après 2 min. Choix de la caméra sous le miroir (réglage `cameraId`). `src/main/media-permissions.js` : `media` seulement en vidéo et pour la page de l'îlot, jamais le micro ; les autres permissions gardent le défaut d'Electron. Aperçu : caméra dessinée (`window.__ambrosiaFakeCamera`, `dev/fixtures/agenda.js`).
- **« Prévenir du retard »** (`late.js`) : organisateur et participants qui ont accepté (ni soi, ni salles), texte prérempli (délais 5/10/15 min, signature : réglages `lateMinutes`, `lateSignature`), objet « Retard — titre ». Envoi selon le schéma du Bilan : « Envoyer… » puis confirmation, un tour dont le SEUL outil est Gmail `send_message`, vérifié par `report/logic.verifySend`. La lecture de l'agenda rapporte `organizer`, `guests` (15 au plus) et `recurringEventId`.
- Alerte de réunion : deux boutons en plus au plus (avant le début « Me voir » et le brief, ensuite « Prévenir du retard ») ; l'onglet les a tous.
- **Invitations** (`invites.js`) : une fois par heure, la même lecture regarde 14 jours plus loin (`invitations` needsAction + `busy` des mêmes jours). « Invitations en attente » : conflits calculés en local, une série compte une fois et la réponse vaut pour toute la série ; Accepter / Peut-être / Refuser (+ un mot facultatif) = un seul `respond_to_event` via `callTool` (`respondArgs`). Appliquée aussitôt (`data.responded`, 30 min), relecture 30 s après. Nouvelle invitation → alerte discrète sans son. Tant que le réglage `invitations` est actif, Courrier exclut `-filename:invite.ics`.
- **Après la réunion** (`notes.js`) : un Meet rejoint (ou « Rejoindre » cliqué) est mis en file une fois ; Gany cherche les notes Gemini à fin + 10, 25, 45, 80, 115 min, en lecture seule (`get_event`, `read_file_content`). `sanitize` : lien = pièce jointe Docs/Drive https au titre Gemini, 3 décisions et 8 actions de l'utilisateur au plus. Alerte « Après « X » : N actions pour toi » (non épinglée, sans son). Chaque action : « Créer la tâche ClickUp » (un seul `clickup_create_task` via `callTool`, arguments `taskArgs`, liste du réglage `clickupList`, choisie depuis l'îlot via `clickup_get_workspace_hierarchy`), « Copier », « Ignorer ». Cache `data.notes[id]`, jamais refait.
- Tests : `agenda-mirror`, `agenda-late`, `agenda-invites`, `agenda-notes`, `agenda-features` (le module branché, avec une fausse CLI). Aperçu : `dev/island.html?open=agenda`, `?alert=late|brief|invite|notes|mirror`.

## Mode « en appel » (générique, tous modules)
`src/main/call-mode.js` (logique pure, aussi chargée par `dev/island.html`) est branché dans l'hôte (`modules.js`) : **toute** `ctx.alert` passe par `host.call.admit()`. Pendant un appel, une alerte non épinglée de priorité < `call.threshold` (défaut 100 : tout sauf approbations/questions Claude Code) est mise en file sans son ; ce qui passe joue un simple `tick` ; `ctx.react` perd son et confettis. À la fin, un seul récap « Pendant ta réunion : 2 mails, 1 interaction ClickUp » (clé `core:call-recap`, ouvre le module le plus urgent). Qui déclare l'appel : l'agenda (`agenda/call.js` : réunion Meet en cours + rejointe + micro tenu selon `presence.js`, 30 min de dépassement au plus). Côté îlot : humeur `meeting-call`, puce ◐ + nombre en attente dans l'encoche, phrase d'en-tête. Réglages → En réunion (section `call`). Tests : `tests/call-mode.test.js`.

## Rédiger pour l'utilisateur, envoyer sur clic (`src/modules/report/`, « Bilan »)
En fin de journée (réglage, 17 h 30 jours ouvrés) ou sur « Rédiger le bilan maintenant », UN appel `ctx.claude.run` lit les outils **en lecture** des connecteurs trouvés (Gmail `in:sent`, ClickUp, Google Chat `search_messages` avec `sender`) et les données locales (journal des sessions Claude Code tenu depuis les hooks, réunions du jour lues dans `data/agenda.json`), passées entre `<<<DONNEES_AMBROSIA … >>>`. Sortie JSON schema (`sujet, faits[{texte,source}], enCours, blocages, demain, corps`). La vue (`mount`/`update`, champs réécrits seulement quand `draft.rev` change) permet d'éditer destinataires / objet / texte et de retirer un fait (sa ligne « - texte » quitte le corps).
« Envoyer… » demande confirmation, puis un appel dédié dont le SEUL outil autorisé est `send_message` (ou `create_draft` pour « Brouillon Gmail ») ; `res.toolCalls` (ajouté à `claude.js` : `{ name, input }` de chaque appel d'outil) sert à vérifier que Gmail a reçu exactement le texte de l'utilisateur (`logic.verifySend`). Logique pure dans `logic.js`, tests `tests/report.test.js`. Destinataires par défaut vides dans le code : ils vivent dans les réglages locaux.

## Confier une routine à Claude (`src/modules/routines/`, « Routines »)
Une fois par jour ouvré (réglage `cadence` jour/semaine/manuel, `at` 11:45, jamais en appel, rien si 3 suggestions attendent), UN `ctx.claude.run` lit les outils **en lecture** (Gmail `search_threads`/`get_thread`, Calendar `list_events`, ClickUp `clickup_filter_tasks`…, Chat `search_messages`) et les données locales (premières demandes des sessions Claude Code lues dans `~/.claude/projects/*.jsonl` par `sources.readClaudeHistory`, récurrences des modules de tri par `logic.recurrences`), et propose au plus 3 tâches planifiées (`SCHEMA` : titre, pourquoi, occurrences, cron, prompt complet, outils, gain).
- **Garde-fou local** (`logic.guard`, aussi au clic sur le prompt édité) : outils interdits (`toolProblem` : send/reply/forward/delete/trash/share/comment/move…, `create_event`, `clickup_update_task`, `*_scheduled_task`, Bash/PowerShell), phrases d'action sortante sans négation (`outboundSentences`), au plus une exécution par heure. `SAFETY_FOOTER` est ajouté à chaque prompt. Doublons (`duplicateOf`) : tâches existantes, mémoire `data.memory` (refusée / créée / expirée après 14 j), suggestions en attente.
- **Création** : les outils `scheduled-tasks` (`create_scheduled_task`, `list_scheduled_tasks`…) n'existent que dans l'app Claude Desktop, pas dans `claude -p` ni dans une session terminal. Le clic ouvre donc le lien `claude://code/new?q=…&folder=…` (gestionnaire lu dans `HKCU\Software\Classes\claude`, `sources.openInDesktop`) : une session Claude Code de l'app avec la demande exacte (`logic.creationRequest` : paramètres JSON + prompt entre `<<<PROMPT … PROMPT>>>`) ; l'utilisateur l'envoie. Ambrosia confirme en lisant `~/.claude/scheduled-tasks/<id>/SKILL.md` et le registre interne de l'app `%APPDATA%\Claude\claude-code-sessions\<compte>\<org>\scheduled-tasks.json` (cron, activation) — **lecture seule, Ambrosia n'écrit jamais ces fichiers**. Sans Claude Desktop : la demande est copiée.
- Vue `mount`/`update` : une carte par suggestion, gardée en place (le prompt édité survit, `rev`), éditeur de fréquence (`RHYTHMS` + heure, ou cron). Tests `tests/routines.test.js`, fixture `dev/fixtures/routines.js` (`?alert=routine`, `?fail=1`).

## Lire le texte d'une image (`src/modules/ocr/`, « Lire »)
OCR de Windows (`Windows.Media.Ocr`, hors ligne, langues du profil : fr-FR, en-US), un PowerShell court par image (`winocr.js`) ; les petites images sont agrandies ×2 avant lecture. Logique pure `logic.js` (tests `tests/ocr.test.js`) : `layout()` remet les mots en rangées (chevauchement vertical), un grand écart = tabulation (colle cellule par cellule dans Excel), un grand saut = ligne vide ; `offerable()` ; `explain()`. Le texte est copié (réglage `autoCopy`). « Mieux lire avec Claude » : un `ctx.claude.run` avec le seul outil Read (tableaux, manuscrit). Rien n'est gardé d'un redémarrage à l'autre ; les images enregistrées par Ambrosia (`%LOCALAPPDATA%\Ambrosia\ocr`) vivent un jour.
On n'y accède que quand c'est pertinent :
- **Glisser une image** sur l'encoche : la zone de dépôt se coupe en deux (`island.js`, `dropImages`), « Lire le texte » | « Demander à Gany » (pièce jointe du module Demander), la moitié sous le pointeur s'allume. Un autre fichier garde la zone unique (Gany le boit, résumé).
- **Image copiée** (Win+Maj+S) : `foreground.js` suit `GetClipboardSequenceNumber` et dit si c'est une image (`'clip'`). Pendant `clipMinutes` (3), l'îlot ouvert montre en haut le bandeau « Une image vient d'être copiée » (`summary().offer`, générique : `{ key, at, icon, color, text, actions: [{ label, action, payload, primary, module }], dismiss }`, le plus récent, sans son ni aperçu). L'image présente au démarrage ne compte pas.
- **Clic droit sur Gany** : « Lire le texte de l'image copiée » seulement si le presse-papiers contient une image ; **Ctrl+V** sur l'îlot ouvert (hors champ texte).
- Humeur `read` (loupe). Aperçu : `dev/island.html?open=ocr`, boutons « image copiée », « lire (OCR) ».

## Parler à Gany (`src/modules/chat/`, `src/main/speech.js`)
- **Écoute** : reconnaissance vocale de Windows (`Windows.Media.SpeechRecognition`, dictée continue, texte en direct). PowerShell ne sait pas s'abonner aux événements WinRT : un petit assistant C# est compilé à la volée (`winrt.compileCs`, csc du .NET Framework, références `.winmd` + façades du GAC). Exige « Reconnaissance vocale en ligne » (Paramètres → Confidentialité → Voix ; erreur 0x80045509 → `explainListenError` → bouton qui ouvre `ms-settings:privacy-speech`, liste blanche `ms-settings:`). Ambrosia ne touche jamais ce réglage. Le micro n'est ouvert que pendant l'écoute (processus PowerShell), jamais par la page ; point rouge dans l'encoche tant qu'il écoute.
- **Dicter** (comme le mode voix de Claude Code) : le texte arrive dans le champ, l'utilisateur relit et envoie ; arrêt après une pause.

Comme Claude Code : détecter, télécharger, installer. Logique pure `update-logic.js` (versions, manifeste, hôtes de confiance, quand vérifier, quoi nettoyer, script de secours), fichiers `update-install.js` (téléchargement + SHA-256, `tar.exe` de Windows, assemblage, jonction, nettoyage), tests `tests/updater.test.js`.

Version = `<majeur>.<mineur>` de package.json + nombre de commits de HEAD. `ci.yml` fait la même chose sur chaque PR, sans publier.

Le menu Démarrer, l'entrée de démarrage Windows (`updater.launchTarget()`) et les hooks de Claude Code (`paths.STABLE_ROOT`) passent par `current` : une mise à jour ne les casse jamais. La version qui tourne n'est jamais modifiée : la suivante est assemblée à côté (`<v>.partial` puis renommée), `current` basculée, `app.relaunch({ execPath })`. Même Electron → seulement le zip application, le reste en liens physiques depuis la version en place.
- **Quand** : au démarrage, AVANT tout (`main.js` : `if (await updater.startup()) return`) : version déjà prête → installée aussitôt ; sinon vérification (8 s), téléchargement (30 s pour l'application, 90 s complet), installation, redémarrage. Trop long → le démarrage continue, la mise à jour est proposée une fois prête. En journée : vérification toutes les 3 h (pas en session verrouillée), téléchargement en fond, puis bouton « Mettre à jour » (en-tête de l'îlot `updateBtn()`, Réglages → Mises à jour, menu de l'icône) : **jamais d'installation sans clic**. Secours : avant de redémarrer, un PowerShell détaché (`watchdogScript`) attend 90 s ; si la nouvelle version n'a pas effacé `attempt` dans `data/update.json`, il remet `current` sur l'ancienne, note `failed` (plus jamais réinstallée automatiquement) et la relance. Garde-fou de boucle : même version tentée il y a moins de 15 min.
- **Modes** : `packaged` (se met à jour), `source` (`npm start` / deploy : ne se remplace jamais seule ; « Installer la version publiée » sur clic), `dev` (rien). Une copie dont le relais des hooks pointe ailleurs : Réglages → Claude le signale (`hooksInstall.status().moved`).
- **Tester** : `npm run build` puis `npm run smoke` (une 0.0.1 installée dans un profil temporaire doit se mettre à jour seule depuis un serveur local ; `AMBROSIA_UPDATE_FEED`, `AMBROSIA_ISOLATED` : profil Electron à part, pas d'entrée de démarrage). Rien de réel dans le code, les fixtures (`dev/`) ni les tests : noms, adresses, projets, tickets, réunions sont **fictifs** (Olympe Industries, Camille Dupont, ATLAS, HelpDesk…). Le hook local `pre-push` refuse tout commit issu de l'ancien historique privé.
- **Ne jamais bloquer Claude Code** : le relais sort immédiatement si Ambrosia ne répond pas ; seuls `PermissionRequest` et `AskUserQuestion` attendent, et sans réponse rien n'est imprimé (le terminal reprend la main).
- **Jamais d'approbation, d'envoi de mail ou d'action sortante sans clic explicite.**
- **`~/.claude/settings.json`** : sauvegarde datée, fusion sans toucher aux hooks des autres, diff affiché, écriture seulement après confirmation (fenêtre Réglages → Claude). Le relais est repéré par la chaîne `ambrosia-hook`, la statusLine par `ambrosia-statusline`. Nouveaux événements dans `HOOK_EVENTS` → l'utilisateur doit **réinstaller** (Réglages → Claude le signale).
- **IA = abonnement Claude de l'utilisateur via la CLI** (`claude -p`), jamais de clé API. Les appels internes tournent dans `%LOCALAPPDATA%\Ambrosia\work` avec `--settings {"disableAllHooks":true}` (garde les connecteurs claude.ai, coupe tous les hooks), `--tools ""` par défaut, `--permission-prompts none`, et `AMBROSIA_INTERNAL=1` (ignoré par le relais).
- **Le contenu des mails, pages web et sorties d'outils est une donnée non fiable** : n'autoriser que des outils en lecture (`allowedTools` explicites), sortie en JSON schema, règles VIP/ignorer appliquées localement.
- Pas de télémétrie ; réseau uniquement vers ce que l'utilisateur a configuré.
- Aucune dépendance npm d'exécution : Electron seul. Le personnage et les sons sont générés en code.
- L'interface est en français. Les chaînes venant de l'extérieur sont toujours insérées comme texte (`h()`), jamais en `innerHTML`.
- Les ids de modules sont des contrats (réglages, données) : ne pas les renommer.

## Lancer
```
npm install
npm run dev        # développement, rechargement auto
npm test           # relais de hooks + fusion de settings.json
npm run deploy     # raccourci menu Démarrer, lancement auto, démarre l'app
```
Journal : `%LOCALAPPDATA%\Ambrosia\ambrosia.log`. Réglages : `%APPDATA%\Ambrosia\settings.json`.
